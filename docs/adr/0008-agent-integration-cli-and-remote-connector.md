# ADR-0008：本机 Agent 以 CLI 为基础契约，云端个人 Agent 通过服务端中继的远程 MCP 连接器接入

- 状态：已接受
- 日期：2026-10-30

## 背景

Workroam 需要让 Agent 自己发起推送、拉取并读写交接文档。Agent 分为两类，能力差别很大：

- **本机 Agent**：Claude Code、Codex、Grok Build、Antigravity 等编码 Agent，运行在项目所在的电脑上，能读写项目文件、执行命令，大多也能加载本地 stdio MCP server 和项目级 Skills。
- **云端个人 Agent**：Grok Bot（xAI）、Muse（Meta）等，运行在服务商的云端，用户在手机或网页上与它对话。它们碰不到用户电脑上的文件、命令行和本地 socket，扩展方式只有两种：添加远程 MCP 连接器（公网 HTTPS，Streamable HTTP 传输，OAuth 或 Authorization 头认证），以及上传 Skills（`SKILL.md`）。Grok Bot 的例行任务还能通过 webhook 触发。

原设计只覆盖了本机 Agent：接入项目时在 `AGENTS.md` 写入“工作区同步”约定，Agent 照约定调用 `workroam` 命令行；`workroam mcp`（stdio）计划在 v0.3 提供。这对云端个人 Agent 完全不可用，文档中也没有说明“一键接入”具体是哪一步。

约束：必需的服务端只有 S3（ADR-0001）；数据端到端加密，加密密码不离开用户设备；所有同步都由用户在设备上确认。

## 决定

1. **本机 Agent 以 CLI 为基础契约（v0.1）。** 所有命令支持 `--json`，输出带版本号的稳定结构，配合稳定退出码，非交互可用。只要 Agent 能执行命令就能接入，不依赖 MCP 支持。
2. **用一个 Workroam Skill 教会 Agent 何时、怎样调用（v0.1）。** 接入项目时生成 `.agents/skills/workroam/SKILL.md`，按适配器链接到各 Agent 的 Skills 目录；`AGENTS.md` 中的“工作区同步”约定只保留几行，指向这个 Skill。
3. **本地 stdio MCP server 是可选的增强（v0.3）**，供偏好工具调用或不便执行命令的 Agent 使用，调用同一套 IPC，授权规则相同。
4. **云端个人 Agent 通过可选的 `workroam-server` 提供的远程 MCP 连接器接入（v0.3）。** 服务端在 `https://<域名>/mcp` 提供 Streamable HTTP 的 MCP 端点，自己充当 OAuth 授权服务器；用户设备上的 `workroamd` 主动与服务端保持一条出站连接，服务端把工具调用转发给目标设备执行，结果原路返回。服务端不保存工具调用内容，只记录元数据。
5. **授权在设备上完成。** 服务端没有用户账号：云端 Agent 发起 OAuth 授权时，服务端页面显示确认码，用户在桌面卡片上核对确认码、选择权限（只读 / 可请求同步）和可访问的项目，设备签发授权后服务端才发放令牌。每个连接单独授权、可随时撤销，卡片上显示为发起方。
6. **远程工具最小化。** 只提供状态、项目列表、历史、读取 `HANDOFF.md`、请求推送与拉取；不返回项目中的其他文件内容，不暴露任何密钥。远程发起的推送和拉取每次都要在设备卡片上确认，不能被“1 小时内不再询问”放宽。
7. **`workroam-server` 的中继模式足够轻量，可以由 bot 部署在它自己的云端电脑上。** 中继模式是一个静态链接的单文件二进制，不需要 Docker、数据库或 root 权限，空闲内存不超过 30 MB，全部状态是一个小 JSON 文件；它不持有存储凭证和加密密钥，不读写存储。桌面应用生成带一次性绑定码的部署说明，用户转发给 bot，bot 在云端电脑上安装、启动并回报公网地址（没有对外端口时用出站隧道）。配对码、设备凭证、推送转发、Web 界面属于完整模式，需要存储管理员凭证，只部署在用户自己的服务器上。
8. **设备自己执行授权。** 每个中继请求由设备按自己签发、未撤销的授权核对工具与项目，不信任中继转来的权限声明，所以中继放在第三方云端电脑上也无法越权。
9. **接入方式写进适配器数据文件。** 适配器新增 `[connect]` 段：本机 Agent 描述 Skill 与 MCP 的落点，云端 Agent 描述连接器设置入口、传输方式、认证方式和 Skill 上传方式。桌面“Agent”设置页据此提供一键接入。

## 被否决的方案

- **只用 CLI**：对本机 Agent 足够，但云端个人 Agent 无法执行用户电脑上的命令。
- **让云端 Agent 在它自己的云端电脑里安装 CLI，作为一台设备加入工作区**：加密密码和仓库密钥要交给第三方云，违背端到端加密；云端电脑上也没有用户的项目文件。
- **本机后台服务直接对公网提供 HTTP MCP**（端口映射或每台设备各开隧道）：攻击面暴露在每台设备上，设备换网络后地址失效，云端 Agent 需要分别连接每台设备。
- **云端 Agent 直接读写 S3**：需要把访问密钥和加密密码交给第三方，同上。

## 后果

- 本机 Agent 在 v0.1 就能可靠接入，CLI 的 JSON 输出与退出码成为需要保持兼容的公开接口。
- 云端个人 Agent 依赖一个中继模式的 `workroam-server`，并且至少有一台设备在线才能执行操作；有云端电脑的 bot 可以自己部署中继，用户不需要准备服务器；设备离线时，推送与拉取请求可排队 24 小时，设备上线后弹出确认卡片。
- TLS 在中继终止，工具调用的参数和结果会经过中继；中继放在 bot 的云端电脑上时，这些内容本来就要返回给同一个服务商，暴露范围没有扩大；返回给云端 Agent 的内容（状态摘要、`HANDOFF.md`）会进入服务商的云端，不再受端到端加密保护。因此远程连接默认关闭，按项目开启，并在开启时明确提示。
- 云端 Agent 的连接器入口与认证方式由服务商决定，变化较快，需要通过适配器数据跟进。
- bot 的云端电脑可能重启或被回收，临时隧道的地址会变；需要推荐固定地址，并在地址变化时由 bot 回报、用户更新一次。中继不保存数据，重新部署后重新绑定即可。
