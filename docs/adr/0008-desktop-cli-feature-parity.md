# ADR-0008：桌面应用与命令行功能对等，由同一份功能清单约束

- 状态：已接受
- 日期：2026-10-30

## 背景

Workroam 有两类使用场景：日常在桌面应用（托盘、卡片、主窗口）里点按，以及在没有图形界面的机器、脚本或 Agent 调用中使用命令行。ADR-0005 已经让初始化向导与 `workroam setup` 共用一套实现，但其余功能（项目、推送拉取、授权、历史、归档、设备、设置）在早期文档里只在一侧描述，或两侧的参数与默认行为不同，例如桌面“拉取”总是获取租约，而命令行写成 `pull [--acquire]`；托盘的“暂停自动同步”和设置页的全部选项没有命令；`prune`、`verify` 没有桌面入口。

只靠评审很难长期保持两边一致：每加一个功能，都可能只做了一侧。

## 决定

- **每一项面向用户的功能在桌面应用与命令行中都有入口**，两者调用同一个 IPC 方法；业务逻辑、校验与默认值只在 `workroamd` 一侧实现，两个客户端只收集输入、展示结果（扩展 ADR-0002 与 ADR-0005）。
- **只在一侧存在的能力必须列入豁免清单**，且仅限展示形式（托盘图标、卡片位置、外观）、输入方式（扫描二维码）和给机器用的接口（`workroam mcp`、`--json`、退出码、shell 补全）。
- **同一功能两端同一版本交付**；因此桌面同步历史提前到 v0.1、桌面归档页提前到 v0.2。
- **功能清单随代码维护**：`crates/workroam-ipc/parity.toml` 为每个功能登记 IPC 方法、命令行命令、桌面操作 ID 与首次交付版本；CI 检查清单完整、命令能被真实的 clap 定义解析、桌面操作存在、版本一致，并由清单生成 `docs/cli-ui-parity.md`（技术架构 §16.4）。
- 命令行交互式提问与桌面界面使用同一份中英双语文本，确认步骤一致；非交互模式必须用显式参数确认。

## 后果

- 用户在任一入口学会的操作，在另一入口用同样的概念完成；Agent 与脚本能做到桌面上能做的一切，同步授权除外（仍需人确认，SEC-05）。
- 命令数量增加（`config`、`approval`、`job`、`handoff`、`password`、`credentials`、`pause` 等），需要保持“名词 + 动词”的命名一致。
- 每个新功能都要同时设计两端入口并更新清单，开发成本略增；换来的是不会出现只有一侧能做的事情。
- 桌面应用需要导出操作清单（`apps/desktop/actions.json`），供一致性检查使用。
